# ADR-001: 模块化单体优先

- 状态：[Current]
- 日期：2026-09-14

## 背景

GuliangIAM 是全新建设项目，团队规模与部署形态在项目初期都不支持多进程拆分：认证、用户、组织、授权、会话、审计之间存在大量强一致写入（例如签发令牌必须与授权码置废、会话写入、审计落库在同一事务内完成）。此时若先拆微服务，分布式事务、跨服务审计关联、调用链运维与部署编排的成本会立即发生，而“独立扩容、独立发布”的收益尚无对应需求支撑。与此同时，单体不等于无结构：必须在同一进程内先把模块边界做硬，未来触发拆分信号时边界可直接平移为进程边界。

## 决策

认证、用户、组织、授权、会话和审计先部署为模块化单体，通过 Domain Port 和构造函数注入隔离边界，不立即拆分微服务；`internal/bootstrap` 作为唯一组合根负责装配。

## 理由与后果

- 正面：IAM 核心写入可使用本地强一致事务；本地开发、CI 与生产部署形态一致；调试链路短；表结构可按 ADR-022 的单一幂等 DDL 统一演进。
- 负面：容量上只能整体水平扩容（无法只放大热点模块）；模块边界只能靠分层门禁与评审长期维护，一旦门禁松弛会退化为“大泥球”；单进程的致命故障影响全部模块，故仍需配合限流（ADR-019）、SLO（ADR-020）等可靠性措施。

## 替代方案

- **先拆认证微服务（auth-service 独立部署）**：放弃理由——当前不存在独立团队、独立故障域与容量瓶颈，拆分立即引入网络边界、分布式事务与跨服务审计关联问题，成本确定而收益为假设；该方案在复审信号齐备时可重新评估。
- **仅靠包/目录约定的“礼貌式单体”**：放弃理由——目录约定没有强制力，历史经验表明分层违规只能在评审中偶然发现；因此采用 Domain Port + 构造函数注入 + `scripts/check-layers.sh` 门禁的硬约束组合（见 ADR-005）。

## 验证证据（Current）

- `ls internal/`：代码按 `domain/`、`app/`、`infra/`、`transport/`、`bootstrap/`、`platform/` 分层；组合根位于 `internal/bootstrap`（`runtime.go` 的 `uuidGenerator := platformuuid.V7Generator{}` 完成 UUID 生成器等基础设施注入；行号随代码演进，以符号定位）。
- `go build ./...` → 退出码 0，全部生产代码在单进程内编译链接通过。
- `bash scripts/check-layers.sh .` → **ALL CHECKS PASSED（9 条规则全部 0 违规，核验 2026-11-21）**：Rule 1（`app/ → infra/`）、Rule 2（`transport/ → domain/`）、Rule 3（`domain/ → infra|app`）、Rule 4 `fmt.Errorf` 包装风格、Rule 5 stdlib log、Rule 6 `TODO(phase3)`、Rule 7/8 越层依赖（informational 计数，当前均为 0）、Rule 9 `superAdminCtx` 回潮全部 0；历史告警已逐项清零（见 ADR-005）。

## 复审条件

出现明确容量瓶颈（单进程垂直扩容到上限仍不满足）、独立故障域需求、独立发布节奏，并且跨模块一致性方案（Outbox / 事件，见 ADR-008、ADR-017）已就绪时，复审是否将某模块拆分为独立服务。Rule 2 历史告警已清零并补登全绿证据（见验证证据），该触发条件已履行。
